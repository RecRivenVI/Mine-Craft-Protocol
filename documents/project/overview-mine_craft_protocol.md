# Mine Craft Protocol 产品导览

Mine Craft Protocol 是让 Agent 在真实 Minecraft 中完成自动测试的平台：理解当前实例，准备条件，执行操作，等待实际结果，判断是否符合预期，再留下可解释的证据。它既能代替玩家操作，也能在不接管键鼠时观察、诊断或配合玩家；这里的“自主”首先指完成测试闭环，尚不表示能长期独立游玩。

## 先看这一页

可以把它理解为 Minecraft 内的一套观察、操作和测试接口。Agent 不必先从截图猜按钮：它能读取界面控件、文字和槽位，读取客户端已经接收到的附近世界，用真实输入操作；取得额外授权后，也能查看内部状态、建立夹具或执行明确的调试修改。原生 HTTP/WebSocket 接口和 Model Context Protocol Companion 服务提供两种入口。

例如测试熔炉：先找到并打开熔炉，用语义槽位放入原料和燃料，等产物出现，再核对背包。如果没有产物，Agent 可以在获准的情况下读取内部状态，区分燃料、配方或同步问题。报告必须说明哪部分是真实玩家操作，哪部分用了调试准备，不能把“输入已发送”当作“测试成功”。

**目前是已有可用 Alpha 和大量有限自动证明、仍需集中真人接受的状态。** 五个 Target 已实现核心控制、UI、世界、调试、采证和三种部署的重要路径。本地扩展平台已交付七个首批扩展包；原生扩展包配置流程完成过专门合作验收。UI 和世界两个完整里程碑尚未获得统一人工接受，不能用测试数量换算完成比例。

最值得先记住四条边界：

- READ 只读；OPERATE 可执行获准操作但不接管键鼠；TAKEOVER 持有控制租约后接管玩家输入。模式本身不授予权限。
- USER 表示玩家路径或相应主体可取得的数据；DEBUG 表示内部观察和调试路径。三种模式都可按独立授权读取两类数据，调试修改另需授权与前置条件。
- 只有客户端具备游戏画面与键鼠表面。独立服务器提供自己的控制台和世界接口；双端联动需要服务器明确委托。
- 扩展包是经本机批准的受信任 Java 代码，不能当作安全沙箱。它扩展可读、可操作的范围，但不自动授予 Agent 高权限。

想实际使用，读[安装与使用](../usage/guide-installation.md)；想判断当前交付，读[状态页](status-milestones.md)和[集中合作验收清单](../development/testing-cooperative_acceptance.md)。范围由[Core](scope-core.md)与[可选扩展](scope-extensions.md)负责，下面只解释它们如何组成产品。

## 界面、背包与玩家看得到的信息

界面树把原生按钮、输入框、列表、容器槽位等内容转换成语义目标，包含文字、位置、大小、可用性及相应操作。列表滚动条、富文本链接、书本、告示牌、聊天建议、进度画布和特殊菜单有各自的原生适配。HUD 与 Toast 的呈现内容也可读取；没有可操作入口的内容不会假装成按钮。

Agent 可以按目标身份执行 hover、点击、拖拽、滚动和文字输入，不必自行维护固定坐标。真实操作经过虚拟指针和 Minecraft 的原生输入路径；点击前重查界面、目标和几何，旧目标失效时明确拒绝。文字或物品状态变化后，需要重新读取，不能盲目重放先前点击。UI DEBUG 则另行提供批准的内部读取、强类型编辑和诊断，用于测试准备及定位问题。

这些机制已有五端具名自动场景。它们证明相应控件和流程的行为，不证明每个原版界面、所有输入法和任意第三方自绘 UI 都已人工体验过。未知界面仍可在授权下使用截图与坐标兜底。Companion 网页控制台只是体验接口的测试页面，不承担产品配置或扩展管理业务。具体机制见[运行架构](../design/architecture-runtime.md)，验证范围见[UI 验证](../../validations/conformance-vanilla_ui/validation.md)。

## 世界感知与真实玩家动作

世界 USER 读取采用“有界客户端世界模型”：在明确范围和预算内返回客户端已经接收到的方块、实体及玩家状态，不严格限于当前画面可见部分。它可能读到墙后或地下的已接收数据，因此不是防透视边界；也不会为了回答问题加载新区块、读取磁盘或取得服务器内部数据。附近场景、区域分页和目标引用帮助 Agent 先发现目标，再瞄准和交互。

玩家动作包括持续移动与转向、挖掘和连锁破坏、精确放置、主副手持续使用、蓄力、战斗、载具及具名实体交互。瞄准、距离、碰撞、冷却、手持物和服务器规则仍由游戏校验。持续按键可以跨请求保留，但仍受租约、期限和取消清理约束。语义目标被发现，不表示它已经可达或可以隔墙操作。

世界 DEBUG 可以在授权下检查服务器权威状态，并对批准的方块、实体、玩家、背包、环境、关系或有界区域执行强类型修改。资源版本、世界身份和执行前检查用于防止修改过期目标；批次可能部分完成，恢复原值也不是事务回滚。放置、命令或输入的 Operation 完成后，还应通过独立世界状态确认效果。已有五端有限场景证明；动态 Boss、任意模组业务和长期自主导航不在这些结论内。目录和限制见[世界控制设计](../design/concept-world_control.md)及[世界验证](../../validations/conformance-world_read/validation.md)。

## 与真人协作、命令和授权

Agent 可以在 READ 中观察玩家游玩，在 OPERATE 中执行不占用共享键鼠的获准工作，也可以在 TAKEOVER 中代替玩家。TAKEOVER 期间真人游戏输入被阻断，物理 Esc 立即撤销接管、取消相应活动和排队输入、释放按住状态；宿主系统快捷键不受阻止。Agent 路由的 Esc 仍是普通游戏输入。

物理 Esc 只结束接管，不自动停止所有独立 DEBUG 工作。Runtime 保留需要重新同意的状态，Agent 必须结合用户决定是否继续合法的非接管工作；再次接管前取得用户当前同意。Runtime 不能验证聊天里的同意文本。同一令牌下的多个模型也不是独立安全账号。

命令全部归 USER，包括需要作弊或管理权限的命令。原生命令树用于发现当前主体实际可用的入口，但不替代授权，也不保证执行成功。OPERATE 可以通过正常玩家命令 API 提交单条或有界批次，无需抢键鼠或打开聊天框；共享聊天输入仍属于接管路径。服务器控制台使用独立操作员主体和获准目录，不能变成宿主 shell。

认证、scope、Control Lease、Debug Arm、服务器权限、资源前置条件和证据来源分别生效。UI 的授权不能变成服务器写权限；有 OP 也不会凭空获得服务器内部通道。自动化已验证多种撤销和失败路径，真实撤权、焦点、宿主光标、输入法及整体合作体验仍应按清单验收。当前合同见[控制模型](../design/concept-agent_control.md)和[威胁模型](../design/security-threat_model.md)。

## 深层状态、存档只读与测试闭环

普通观察负责 Agent 当前需要的场景信息；Deep Observation 进一步提供强类型玩家、实体、方块实体、区块加载和计划 tick 等内部状态。Provider 是可扩展的结构化观察入口，必须声明数据形状、读取类别、执行线程、预算和生命周期，不能借“通用扩展”开放任意对象反射。

这些接口区分客户端已知、服务器权威和上次保存的数据。Persistent Read 能在安全上下文中有界读取存档，明确忙、锁定、过期或不可用；它不是实时世界的另一份真值，也不接受调用方任意文件路径。正式 Persistent Write 尚未实现，已有写安全基础和诊断实验不能算作可写存档功能。

测试按“准备 → 操作 → 观察／等待／断言 → 采证”组合。Fixture 建立测试前提，条件引擎等待真正满足的 UI、世界、事件或 Provider 状态，Operation 和事件通道表达进度、终态、取消、断流及恢复。调试准备不冒充正常玩法，通过接口发出动作也不自动成为通过断言。现行[Native 合同](../reference/protocol-native_v0.md)和[深层状态计划](plan-deep_state.md)解释精确范围。

## 截图、录制与可解释证据

Capture、Recording、时间线和 Artifact 将画面、结构化状态、事件及断言整理成可以导出的证据。默认画面读回发生在控制边框、接管提示和虚拟指针绘制之前，因此这些操作员界面不会污染测试截图。独立服务器没有截图，使用适用的控制台与结构化录制表面。

证据保留 PLAYTEST、FIXTURE、DEBUG_PRIVILEGED 等来源。预算耗尽、缺帧、派生图生成失败或操作效果未确认，不能被包装成完整成功；录制本体和 contact sheet 等派生产物也应分别解释。截图仍可能包含用户内容，排除控制界面不等于匿名化。

当前可以解释一次具名测试发生了什么，尚不能重建任意时刻的完整游戏。受控 keyframe／差分／重建实验存在，但正式高级录制、长期规范存储、完整状态重建、滚动录制、Human Replay 和高级崩溃恢复仍是后续设计，不能从普通录像或实验样片推定。现状与后续 Core 门槛见[深层状态计划](plan-deep_state.md)。

## 如何安装、连接与跨客户端／服务端使用

Runtime 在本机启动并自动分配端口，实例发现记录帮助 Companion 按明确实例连接。握手和启动身份防止旧端点或实例重启后串连；发现本身不授予令牌、权限或接管。Native HTTP/WebSocket 与标准 Model Context Protocol 工具共同使用相同的 Runtime 合同，Companion 还提供静态作者规则与扩展文档查阅。

仅客户端安装时，可以观察本地界面、操作真实玩家并读取客户端数据；加入普通服务器也不会自动获得远端内部状态。仅服务端安装时，有独立认证入口、控制台、服务器资源与调试、等待和结构化采证，没有虚构的玩家屏幕或键鼠 TAKEOVER。双端安装时，客户端真实操作与服务器权威观察通过显式、限时、可撤销的连接委托协作；双方权限仍分别检查。

目前五个 Target 是 Forge 1.20.1、NeoForge 1.21.1、NeoForge 26.1.2、NeoForge 26.3 和 Fabric 26.3。对应能力有逐端实现与具名安装、运行证明，不能用一个 Target 推定其他端等价。当前默认是可信本机 Agent 场景，不是公网托管、多租户隔离或任意操作系统均已验收。部署的精确主体和边界见[三种部署](../design/concept-deployment_scenarios.md)，版本事实见[项目规范](../AGENTS.md)。

## 本地扩展平台和七个首批包

扩展平台解决原生通用机制看不到第三方业务语义的问题：通过公共 SDK、各 Loader 加载桥及独立 extensionpack，给既有界面、世界、Provider、Debug 和测试体系补充能力，不要求上游模组主动接入。统一测试与受控探针体系已由用户纳入 1.0 Core，不再全部归为遥远的 E1。

用户在原生模组配置页首次启用包即批准这份固定内容哈希；Agent 可以禁用或重新启用已批准的同一份包。包更新后需要重新批准，代码与 Mixin 变更要重启，不能承诺热卸载。静态查阅不需要世界 DEBUG 权限，但实际游戏读取和修改逐项授权。安全边界是本机受信任代码，不是防恶意 Java 代码的沙箱。

首批已有 CC: Tweaked 终端、Modern UI 框架输入、EMI 搜索／收藏／配方导航、AE2 存储与合成、Create 装配、Exposure 拍摄，以及 LittleTiles 微型几何和交互诊断的有限业务证明。不是七个模组的全部功能：CC 的固定 NeoForge 26.3 上游包启动受阻，LittleTiles 运动中再次选取和完整关闭仍未闭环；其他 Target 没有合适上游版本时，不借别端冒充通过。

平台、七包和 Companion 按固定批次共同分发。原生配置的专门真人流程已完成，复杂框架的真实 IME 与整体体验仍待验收。作者接口和预览面见[扩展平台合同](../reference/api-extension_platform.md)，作者工作流见[扩展包构建](../development/build-extensionpacks.md)。

## 长期方向、研究成果与设计来路

1.0.0 与 Developer Preview 在本项目中是内部成熟度标准，尚无对外公开发布决定。现有 Alpha 说明具名候选可以试用，不代表两个领域已完整接受，也不意味着协议已冻结。高级录制与重建、后续恢复、安全审查和真实复杂环境兼容仍各有未完成项。大型整合包沿用[长期兼容计划](../../validations/compatibility-large_modpacks/validation.md)，本轮没有执行。

E1 保留远程探索式对象／代码调试及额外开发智能；E2 是路径规划、长期自主游玩与策略；E3 是确定性图形验收和渲染取证。三者都不进入当前 1.0 范围。独立主体、Fake Player、第二玩家和同客户端第二界面另有研究，尚未成为本体可调用的正式能力。已有外置导航、图形捕获、隔离适配及第二界面原型，只证明各自环境和场景中的可行性。

设计曾发生几次重要转向：从探针起步扩展为测试平台；控制模式从严格隔离读取转向按输入关系区分、按 USER／DEBUG 标明来源；命令最终统一 USER；世界 USER 从严格画面可见转向有界客户端模型；双端从安装要求转为可选安装与独立主体授权；扩展平台及统一探针测试被明确纳入 Core。这些当前采纳结论见范围与控制、世界、部署设计。产品方向来自用户明确批准，具体实现拆分包含 Agent 建议，研究原型本身不构成采纳或实现授权。

[显式 Target 决策](../design/adr-1-explicit_target_governance.md)、[输入与渲染钩子决策](../design/adr-2-phase0_input_render_hooks.md)、[原生合同决策](../design/adr-3-openapi_v0_contract.md)及[loopback 决策](../design/adr-4-v1_loopback_release_profile.md)保留各自时点的依据。[阶段记录](phase-1-core_delivery.md)和既有研究记录保留历史原文，不能把其中旧限制或 proposal 当作当前状态。仓外四类研究及其源码、输入、捕获和失败记录有独立专题索引；本总览不嵌入本机路径。

## 怎样判断现在的可信程度

当前冻结 Alpha 对应的五个 JAR、清单、手册、120 份扩展交付证明及各自基线继续原样保留。本轮只整理说明和研究资产，没有构建、测试或创造新的产品证明。历史 DP 的原版专项、后来扩展候选的受影响回归和专门合作验收是不同范围，不能拼成一张“全部功能通过”的表。

读某项结论时，要看它证明的是源码存在、自动断言、真实运行、人工体验，还是仅有研究原型。最终包在干净 Loader 中可安装，和所有功能已成熟是两件事；业务步骤有独立效果证据，才足以说明该场景做成。现有架构依靠共享策略与执行器、各 Target 原生适配和独立扩展协作；复杂特殊表面仍有专门适配，不能宣传任意第三方零适配。

眼下需要特别关注的是完整合作验收、已知第三方边界，以及文档中旧“当前候选”“尚未实现”措辞可能落后于交付的问题。本页以现行范围和冻结身份解释它们，未把调查发现自动变成开发任务。下一步由用户安排真人验收及后续开发；当前工作只见[执行计划](plan-execution.md)，不自动恢复旧 Goal 或开启产品阶段二。
